# 后端监测与瓶颈定位报告（2026-10-15）

结论：**本轮公开读取高负载的主要耗时在数据库连接获取阶段，不是单条SQL持续执行很慢。逐次健康检查存在可测开销；增大连接池不能线性提升性能。当前证据不支持更换PostgreSQL、重写Rust后端或认定表设计错误。**

## 交付与当前运行状态

- 新增请求耗时/状态码/在途数/取消数、按请求汇总的DB获取与SQL耗时、SQL摘要执行时长及错误数、成功获取连接时长、连接池占用、worker事件循环延迟。
- HTTP响应增加 `X-Request-ID`。超过500ms的慢请求日志含路由模板与耗时分解，每秒约5条限频；不记录密码、Token、文章正文、查询参数或SQL参数。
- 指标监听 **http://127.0.0.1:39160/metrics**，业务仍为前端39158、后端39157。指标只允许回环IP，业务鉴权/响应体保留。
- Nuxt架构与前端构建未修改。所有修改、本地替换和压测均未上线、未推送。
- 对照结束后恢复原有DB及日志配置，保留本地指标端口。当前仍是默认池上限10、连接健康检查true、最大寿命10秒；诊断中的关闭健康检查/池30没有作为最终生产配置。
- 后端源码基于 `a43ad07` 加本地未提交监测改动；release二进制SHA256：`16a1eff9beb9bd95cf20bb15611585f441cea0653047cd504d340ad3fcbf08a4`。

## 测试范围与有效性

Rust原生release（opt3/LTO）、PostgreSQL17 Docker、525篇本地文章、同机Node发压、回环网络。直接访问Rust API，绕过Nuxt缓存。

固定配比：60%文章详情（遍历525篇）、20%列表（44页、limit12）、10%分类、10%标签。连续60个在途请求，每组20秒；另测3000请求尽快集中发起。无重试，读取完整响应体、检查HTTP200和业务code200，10秒超时。原配置另测1000模拟读者每10秒一次API请求，30秒内3000次。

本轮两批合计 **319,088 次读取请求，失败 0**。这是多组短时控制变量实验，不是长时间耐久测试、所有接口或整站SSR容量验证。工作负载与此前五路均匀混合含prevnext的596RPS测试不同，不把新数字当作同场景的性能提升。

发压发生器保留调度延迟/事件循环延迟，采集应用进程CPU/RSS和PostgreSQL活动等待事件。监测有自身开销，未单独以监测开启/关闭做严格性能对照。原配置1000读者阶段含一次额外健康探针，因此服务端计数3001与业务发压3000略有区别。

## 连续60并发对照

客户端P95为实测分位数；后三列为**服务端每请求平均毫秒**，不能将均值与P95混为一谈。获取连接包含排队、健康检查及新连接建立；SQL包含执行、结果获取及数据库往返。并行操作之和不一定是互斥墙钟阶段。

| 原配置 | 1612.5 | 53.15 | 35.917 | 33.566 | 2.261 | 0 |
| 日志轮转1MiB | 1488.6 | 60.18 | 39.029 | 36.435 | 2.486 | 0 |
| 关闭逐请求/连接日志，池10 | 1111.7 | 99.91 | 52.408 | 48.862 | 3.389 | 0 |
| 关闭逐请求/连接日志，池30 | 729.4 | 219.68 | 79.639 | 64.936 | 14.46 | 0 |
| 原配置重复 | 1507.7 | 58.56 | 38.417 | 35.915 | 2.4 | 0 |
| 连接寿命1800秒，池10 | 1605.1 | 56.59 | 36.104 | 33.756 | 2.256 | 0 |
| 寿命1800秒，关闭逐次健康检查，池10 | 2304.3 | 37.16 | 24.865 | 22.543 | 2.236 | 0 |
| 寿命1800秒，关闭逐次健康检查，池30 | 2411.8 | 46.36 | 23.289 | 16.857 | 6.298 | 0 |

原配置两次基线为1508–1613RPS、P95约53–59ms。首次基线请求平均35.917ms，其中获取连接33.566ms、SQL合计2.261ms；重复基线也得到同一耗时分布。池10被占满，worker计时器P99桶上界约3ms，没有观察到持续的大量worker阻塞。

关闭逐请求日志、加大轮转阈值没有稳定改善结果，不能把之前发现的10KB轮转阈值直接认定为主因。部分阶段发生SQL往返耗时波动，单组对比不能排除同机/Docker调度和时间顺序影响。

将连接寿命由10秒延长到1800秒仅有较小变化，短测不足以断言它是主要瓶颈。寿命1800秒/池10情况下，关闭每次acquire健康检查，吞吐1605.1→2304.3（约43.6%），P95 56.59→37.16ms，SQL合计均值2.256→2.236ms基本不变；这支持额外连接检查往返是限制因素之一。

同样关闭检查后池10→30，吞吐2304.3→2411.8仅约4.7%，P95反而37.16→46.36ms，SQL合计均值2.236→6.298ms。连接增加后底层往返更慢，不应按“并发人数”直接把连接池开大。

## 1000模拟活跃读者复验

每人10秒一个API请求，30秒，约100RPS，共3000次、失败0，客户端P95 **10.44ms**、P99 **14.12ms**；服务端平均3.547ms，获取连接1.434ms，SQL合计1.77ms。这一模型下仍有余量，不等于千人同时打开完整SSR页面。

当前全部命中共享缓冲区，没有本次查询的物理读取。UUID详情具备唯一索引；列表对小表扫描/排序并不自动构成设计错误。将来数据量增大后，应重新测量过滤/排序索引和深分页；列表查询目前会读取部分响应不用的完整模型字段，也有进一步减少数据搬运的空间。

## 验证与保留的限制

- 最终源码后端全量测试 **40通过、0失败**；新增4项验证连接等待与SQL分离、401状态保留、标签不含敏感参数、指标监听拒绝公网IP。
- release构建成功；新增只读EXPLAIN示例编译并运行成功。
- 本地功能回归通过：真实登录/会话脱敏、文章草稿隔离及CRUD、分类标签链接管理、重复/不同访客并发计数、注销撤销Cookie。
- 当前指标HTTP200，实际JWT密钥和管理员密码/账号不出现在指标文本；`.env`保持600权限。
- 本地最终健康/就绪接口200，诊断配置已恢复。
- 监测端口为新加的进程内Prometheus文本导出，并未部署外部Prometheus/Grafana历史存储。重启清零；原始阶段快照已存档。
- 获取连接的失败时长、unprepared SQL、原生SQLx、BEGIN/COMMIT及另行spawn任务不保证全部进入SeaORM回调。请求耗时截至响应准备完成，不包含网络传输、连接接受前等待或流式响应传输。详见后端 `docs/observability.md`。

## 建议顺序

1. 保留监测，目标部署环境先用原配置重跑同负载，关注数据库往返、连接获取等待和P95；不能照搬本机RPS。
2. 将10秒连接寿命调整为与部署环境匹配的合理值，并监测连接建立/断开。短测未证明它是主因。
3. 优先评估“按连接空闲时长健康检查”以减少每次查询前的额外往返；必须补断线恢复、数据库重启、写事务错误处理测试，而非永久关闭检测或自动重试所有写入。
4. 连接池按测得的延迟/数据库总连接预算配置；本轮不支持直接从10扩成很大值。多个实例应合计连接数。
5. 结合实际慢查询做字段投影、索引/分页优化。对当前千名轻度读者目标，无证据要求重写后端或更换PostgreSQL。
6. 整站仍应独立优化Nuxt公开HTML缓存，后端API结果不代表整站SSR通过同等负载。
